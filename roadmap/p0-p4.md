# PASI Engineering Workspace Roadmap

This is the checked-in engineering spine for the automation program. Canonical task eligibility and completion state live in the phase issues; this document records the current architecture-level order and promotion gates.

## P0 — Runtime proof and delivery infrastructure — IN PROGRESS

P0 is the current promotion gate for the CDP network-authority architecture. Historical DOM-path M0/M1/M2 evidence remains historical evidence and does not by itself close the current P0 gates.

**P0 execution model — just-in-time supervised workflow**

P0 acceptance must exercise the same runner/state-machine model that the eventual frontend will control. The runner creates only the next operation required for the current step; it never pre-queues a fixed future batch of prompts. A prompt is not considered predictable merely because its input is known: the next prompt is generated from the runner's current durable state only after the previous operation reaches authoritative terminal response, response-processing acknowledgement, and any required recovery decision. The operation queue is therefore a transport/handoff mechanism, not the workflow/orchestration mechanism.

The frontend/command control is a runner control surface, not a single-prompt dispatcher. The same control must be able to start/resume the selected runner and pause/stop it without creating duplicate operations. M1 uses the common runner with a hard 20-operation acceptance cap; P0.4 removes that cap and terminates only on the 168-hour deadline, explicit pause/stop, or an independently defined terminal condition.

1. **M0 / P0.1 — Current-CDP live task proof** — Prove authenticated submission, CDP Fetch request correlation, authoritative response-stream capture, contract parsing, patch application, validation, commit, and durable evidence.
2. **M1 / P0.2 — Current-CDP twenty-operation chain** — Prove exact operation/controller/tab correlation, terminal network completion, same-conversation progression, and zero duplicate submissions using the common supervised runner; submit exactly one operation at a time and wait for terminal response plus processing acknowledgement before generating the next operation.
3. **M2 / P0.3 — Current-CDP browser/restart recovery** — Establish the browser-session recovery boundary, then prove exact-operation recovery across browser interruption, stale tab/debugger cleanup, bridge restart, and service-worker restart without duplicate prompt submission or unnecessary new-chat creation.
4. **P0.4 — 168-hour supervisor acceptance** — Run only after current-CDP M0/M1/M2 recovery is revalidated. Use the same just-in-time runner and control surface as M1, with no fixed operation-count stop; continue until the 168-hour deadline or explicit pause/stop. Prompt compilation is bounded to the selected task plus minimal completion/continuity context; completed sibling tasks are not injected.

**Post-P0.4 self-validation loop — planned, not part of the current runner contract**

After P0.4 is stable, the runner can become the trigger for change-aware validation of the next runner generation. A completed phase should update a durable phase-health record, launch the modified runner against the actual browser/terminal boundary, collect authoritative evidence, and promote the next phase only when those checks pass. The frontend can then visualize evidence-backed phase states such as **not evaluated**, **validating**, **validated**, or **regressed**, using the project's blue/green promotion language. These indicators are intentionally deferred until the runner can safely pull/code-change/start/test itself; before that point, a static Ready indicator would imply validation that the current system cannot prove.

5. **P0.5 — Acceptance evidence registry** — Keep the durable provenance registry and bind every current-CDP acceptance artifact to the exact code/controller/environment/run identity.
6. **P0.6 — CI/workflow consolidation** — Keep delivery responsibilities distinct and enforce the four-workflow policy.
7. **P0.7+ — Remaining delivery gates** — Runner health, dependency review, benchmark foundation, and release gating remain downstream P0 work.

P0 completion does not mean future work may close on test-green alone. All subsequent work uses `docs/engineering-completion-standard.md`.

## P1 — Control-plane consolidation — PLANNED / BLOCKED ON P0

P1 begins only after current-CDP P0 recovery gates are accepted.

1. **Unified operation state** — Canonical state shared by browser/CDP worker, bridge, planner, runner, recovery, and verification.
2. **Canonical event model** — Durable lifecycle events for dispatch, submission acknowledgement, network start/completion, retry, recovery, verification, commit, PR lifecycle, and failure.
3. **Durable operation ledger** — Reconstruct task-to-request-to-response-to-commit lineage.
4. **Deterministic recovery decision engine** — Distinguish stale-tab cleanup, UI/provider send failures, transport failures, context exhaustion, usage limits, and authentication failures; never retry after authoritative generation evidence.
5. **Failure-signature registry** — Normalize and persist recurring failures with bounded recovery actions.
6. **Bounded repair loop** — Preserve evidence and stop escalating retries when progress stalls.
7. **Runtime-state migration** — Version persistent operation state safely.
8. **Protected core / mutable skill boundary** — Keep supervisory recovery/control immutable from model-authored self-editing.
9. **Shadow self-modification gate** — Test and atomically promote mutable skill/tool changes.
10. **Multi-agent orchestration**
11. **Persistent automation gateway**
12. **Change-aware verification orchestration** — Deterministic verification classification and ordering.

## P3 — Provider-neutral model infrastructure — PLANNED

Add capability metadata, deterministic provider selection, provider health/fallback, local model profiles, and reproducible PASI benchmarks.

## P4 — Typed computer integration — PLANNED

Add explicit capabilities for terminal, IDE, browser, Git, host recovery, resource observation, isolated computer use, browser-session continuity, and multimodal adapters. Computer control remains separate from model inference and never becomes the transport authority.

## Source-of-truth rule

The phase GitHub issues are the authoritative checklist and acceptance contract. Checked-in roadmap summaries must not claim a phase or gate is complete when its canonical issue remains open or current-architecture acceptance has not been revalidated.
