# PASI Engineering Workspace Roadmap

This is the executable engineering spine for the automation program.

The canonical roadmap is the phase/task issue set. This file is the repository-local summary and must not contradict canonical issue state. Calendar dates are planning targets; dependency gates and acceptance evidence control actual dispatch.

## Cross-cutting execution contracts

These contracts apply across P0-P4 and are architectural invariants unless a later roadmap task explicitly changes them with evidence.

1. **Browser session identity is durable execution identity.** The active Chromium/Opera tab and its PASI controller identity identify the authenticated working session. Conversation URLs are metadata/evidence, not the routing or execution identity.
2. **CDP Fetch is the authoritative ChatGPT transport path.** Generation requests/responses are correlated through the extension service worker and CDP Fetch/IO response streaming. Direct replay of private provider HTTP APIs is not an execution strategy. Page-world fetch interception is not authoritative.
3. **CDP Accessibility/Input is the interaction boundary.** Browser interaction should use typed accessibility and input capabilities. DOM inspection may exist as diagnostic evidence, but CSS/DOM selectors are not the authoritative task lifecycle or transport state.
4. **Operation state is ledger-driven.** The durable operation ledger is the source of task/operation truth. Network observations feed correlation/classification; they do not independently become the whole operation state machine.
5. **Readiness is explicit.** The active browser session exposes a readiness certificate containing controller attachment, network interception readiness, observed chat state, conversation metadata, usage-limit/context state, reasoning mode, active operation identity, verification time, and readiness reason.
6. **Queue dispatch is strictly serial and operation-idempotent.** At most one operation is dispatchable at a time. Restart/reconnect must reclaim the existing operation rather than enqueueing a replacement. Stale queued/claimed operations must be reconciled or quarantined before a runner resumes; they must never silently replay because a browser becomes available again.
7. **P0.4 is a supervisor gate, not a model task.** The seven-day acceptance supervisor owns the gate while P0.6+ work can execute during the window. P0.4 is checked only after the full 168-hour evidence window closes successfully.
8. **Session reuse is the default.** A new ChatGPT conversation is created only after explicit, verified context exhaustion. Provider usage limits are blocked states, not permission to create a new chat. Browser/bridge interruptions are recovery events, not reasons to navigate or start over.
9. **Current architecture must be accepted before further architectural replacement.** During a live acceptance run, implementation work should target the selected architecture and prove it through real operations. A replacement architecture requires an explicit roadmap task/branch and fresh acceptance evidence rather than silently changing the system under test.
10. **Tests are necessary but not sufficient.** A roadmap task is real progress only when its implementation reaches the canonical worktree/branch, produces deterministic verification evidence, and leaves durable task/commit/PR provenance. Passing tests without repository progress is not task completion.
11. **Protected core vs mutable automation is deliberate.** The supervisory runner, operation ledger, recovery controls, policy gates, and safety boundaries remain protected. Agent-authored skills/tools/automations are mutable only through shadow execution, deterministic verification, evidence capture, and atomic promotion/rollback.

## P0 — Runtime proof and delivery infrastructure — IN PROGRESS

P0 establishes the runtime proof boundary on which later autonomous engineering depends. It is not complete until its canonical issue and live acceptance evidence agree.

### Acceptance milestones

- **P0.1 — M0 live task acceptance** — completed. One real task crossed authenticated ChatGPT execution, contract parsing, patch application, canonical validation, and committed-worktree evidence.
- **P0.2 — M1 twenty-operation chain** — completed. Consecutive uniquely marked operations were exercised with identity/duplicate/terminal verification.
- **P0.3 — M2 kill/restart recovery** — completed. Same-operation recovery was exercised across runtime interruptions.
- **P0.4 — 168-hour long-run acceptance** — active supervisor-owned gate. The supervisor must immediately hand off to the next incomplete canonical task after terminal verification, preserve one authenticated session, preserve operation/task identity across interruption, avoid fixed hourly scheduling, and capture full-window throughput/recovery/failure/branch/PR/resource evidence. P0.4 is never submitted to the model as a normal coding task.
- **P0.5 — Acceptance evidence registry** — completed. Acceptance artifacts carry durable provenance for code head, controller/deployment, environment, runner, provider, timestamps, and run/task identity.

### Remaining P0 delivery tasks

- **P0.6 — CI/workflow consolidation** — keep test, security, branch-hygiene, development-control, and runner-capability responsibilities distinct; eliminate trigger/job duplication; enforce an authoritative workflow policy; do not add one-off workflows without a durable role.
- **P0.7 — Self-hosted runner health mode** — add scheduled detect-only runner health to the existing capabilities workflow; repair stays explicit/manual.
- **P0.8 — Security dependency review** — add dependency review to the authoritative security workflow rather than creating a standalone dependency workflow.
- **P0.9 — Benchmark workflow foundation** — introduce benchmark execution only once a reproducible benchmark suite exists, as a controlled job in the authoritative CI path.
- **P0.10 — Release workflow gate** — introduce release automation only after distributable artifact, versioning, and release-acceptance foundations exist.
- **P0.11 — Browser recovery without forced navigation** — preserve authenticated browser-session continuity through durable continuation state; do not launch replacement Opera sessions, open unnecessary new ChatGPT tabs, or use reload/navigation as the recovery protocol.

### P0 completion gate

P0 completion requires deterministic implementation tests plus the required live-runtime evidence. A green test suite by itself cannot close P0.4 or retroactively validate an architecture that was not the architecture exercised by the live run.

## P1 — Control-plane consolidation — PLANNED AFTER P0.4

P1 depends on P0.3 and P0.4 and consolidates the durable control plane around the runtime proved in P0.

1. **P1.1 — Unified operation state** — one canonical versioned operation-state model shared by browser, bridge, planner, runner, recovery, and verification.
2. **P1.2 — Canonical event model** — durable events for dispatch, observation, completion, retry, recovery, verification, commit, PR lifecycle, and failure.
3. **P1.3 — Durable operation ledger** — reconstruct task → operation → prompt → response → patch → verification → commit → PR lineage.
4. **P1.4 — Recovery decision engine** — deterministically classify recoverable, retryable, blocked, terminal, and human-required conditions before fallback reasoning is consulted.
5. **P1.5 — Failure-signature registry** — normalize failures across browser, network, provider, Git, parsing, verification, CI, and environment layers.
6. **P1.6 — Repair-loop controller** — bounded resets/retries, evidence preservation, root-cause family counting, and planner handoff when progress stops.
7. **P1.7 — Runtime state migration** — versioned persistent state with validation, safe migrations, and fail-closed behavior on unsafe transitions.
8. **P1.8 — Protected core / mutable skill boundary** — separate the supervisory orchestration/recovery core from agent-authored automation and skill logic.
9. **P1.9 — Shadow self-modification gate** — perform agent-proposed tool/skill edits in an isolated shadow worktree; run syntax checks and deterministic tests; atomically promote passing changes or roll back failing candidates.
10. **P1.10 — Multi-agent orchestration** — typed subagent lifecycle, scoped context, isolated workspaces, budgets, cancellation, result aggregation, and independent verification.
11. **P1.11 — Persistent automation gateway** — durable local gateway for submit/observe/pause/resume/cancel/query operations without coupling clients directly to workers.
12. **P1.12 — Change-aware verification orchestration** — classify changes deterministically as local, backend-major, frontend-major, or cross-layer; run the minimum required verification in a fixed order, with high-risk browser/security/persistence/CI changes always escalating.

## P2 — Planner, scheduler, and engineering memory — PLANNED

P2 turns the proven control plane into a durable planning and memory system while keeping eligibility rules authoritative and model recommendations advisory.

1. **Roadmap lifecycle manager** — version, validate, activate, pause, resume, archive, and compare structured roadmaps.
2. **Bounded child-task generation** — derive bounded, attributable child work with inherited acceptance/dependencies.
3. **Evidence-aware task selection** — use evidence and blocker value as planning signals without allowing advisory ranking to override hard eligibility.
4. **Cost-aware scheduling** — estimate model, compute, latency, and external-resource cost without converting estimates into promises.
5. **Project memory** — persist decisions, assumptions, constraints, failed approaches, designs, and verified conclusions with provenance.
6. **Provenance-aware retrieval** — project-scoped retrieval with source links and isolation.
7. **Context compiler** — deterministically assemble task-relevant context within size/sensitivity boundaries and measure retrieval cost.
8. **Memory compaction** — compress historical working memory while retaining authoritative evidence references.
9. **Cross-run learning** — promote reusable success/failure patterns only when supported by evidence.
10. **GitHub issue task intake/extraction** — treat eligible issues as the durable task source and compile selected requirements into model-facing task context while keeping scheduler/controller internals out of task text.
11. **Procedural skill library** — versioned reusable task-solving and repair procedures with provenance, applicability, review state, and rollback.
12. **Skill retrieval & guarded adaptation** — adapt skills to current repository evidence without silently turning stale/unverified skills into policy.
13. **Cross-session agent memory** — explicit session/project/user-preference layers with provenance, retention, sensitivity, and deterministic compaction.
14. **Persistent job scheduler** — durable inspectable recurrence with timezone, missed-run, cancellation, and restart semantics.
15. **Asynchronous gateway integrations** — terminal/IDE/messaging adapters that preserve operation identity and authorization.

## P3 — Provider-neutral model infrastructure — PLANNED

1. **Provider capability registry** — context, tools, reasoning, latency, locality, hardware, and cost metadata.
2. **Provider selection policy** — deterministic eligibility based on requirements, policy, availability, and resources.
3. **Provider health monitoring** — outages, limits, auth failures, malformed responses, mismatched capabilities, and latency degradation.
4. **Fallback orchestration** — alternate/local providers preserve operation identity and verification state.
5. **Provider setup UX** — connection configuration, capability/cost display, and tests without exposing secrets.
6. **Local model execution** — Ollama as a first-class provider with profiles, concurrency, context limits, and hardware-aware selection.
7. **Stronger local coding tier** — larger coding models when hardware permits, under the same verification boundary.
8. **PASI benchmark suite** — reproducible correctness, repair-rate, latency, tool-reliability, and cost comparisons.

## P4 — Typed computer integration — PLANNED

P4 extends the proven control plane into explicitly typed computer capabilities. Browser automation remains a capability, not a transport hack, and browser-session continuity remains a first-class invariant.

1. **Computer capability registry** — typed host interactions with target scope, permissions, resource limits, and policy ownership.
2. **Native host helper** — OS-specific helper transport only where browser/IDE APIs are insufficient.
3. **VS Code semantic integration** — controlled workspace inspection, editor state, diagnostics, navigation, test requests, and bounded edits.
4. **Browser semantic integration** — stable tab identity, controlled navigation, observations, downloads, attachments, and recovery semantics.
5. **Typed terminal capability** — allowlisted commands with validated arguments, working-directory scope, timeouts, and resource limits.
6. **Application adapters** — bounded Git/file/terminal/CAD/simulation/EDA/visualization adapters as justified by actual tasks.
7. **Controlled writes** — named capabilities, approval policy, audit logging, and independent verification for mutations.
8. **Host recovery automation** — recover stalled managed applications using verified process identity and post-recovery reconciliation.
9. **Host resource observation** — CPU/RAM/GPU/swap/disk/thermal/process/application telemetry correlated with workload behavior.
10. **Isolated computer-use runtime** — sandboxed/virtualized GUI execution that does not require uncontrolled desktop ownership.
11. **Browser-session continuity** — preserve authenticated sessions across interruption and recover from durable continuation state without unnecessary new tabs, forced navigation, or reloads.
12. **Multimodal interaction adapters** — bounded voice/screenshot/image/visual-state capabilities with provenance, redaction, resource limits, and human-visible failure states.

## P0→P4 dependency rule

The roadmap advances by evidence gates, not by architectural fashion. P1 may refine and consolidate the P0 control plane only after P0.4 proves the runtime under continuous use. P2 builds planning/memory above that control plane. P3 adds provider choice behind the same verification boundary. P4 adds typed computer capabilities behind the same operation ledger, authorization, resource, and recovery boundaries.

## Completion standard

Every phase/task requires implementation evidence appropriate to its scope: deterministic tests, security checks, provenance, resource limits, failure handling, and reproducibility where practical. Performance claims require measured benchmarks. AI/optimization changes require shadow-mode evidence before authoritative promotion. Live acceptance must identify the exact tested code head and deployment/controller version so passing evidence cannot be confused with work performed by an older architecture.
